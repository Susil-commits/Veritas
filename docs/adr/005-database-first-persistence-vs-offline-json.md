# ADR 005: Database-First Persistence Architecture vs. Flat File JSON

## Status
**Accepted** (2026-09-23)

## Context
A recurring anti-pattern and major red flag in full-stack educational AI projects is the reliance on flat `.json` files on the local filesystem for operational persistence (such as storing curriculum problems, student progress, session state, or model hyperparameters).

Storing operational domain entities in flat JSON files presents severe architectural liabilities:
1. **Concurrency & Race Conditions**: Python's `threading.Lock` and file renaming (`.tmp` $\to$ `.json`) only protect against intra-process threading conflicts. They offer zero protection across multiple worker processes (e.g. Uvicorn `--workers 4`, Gunicorn, or Celery workers) or multiple container replicas behind a load balancer.
2. **Horizontal Scalability & Ephemeral Storage**: In cloud-native containerized environments (Kubernetes, AWS ECS, GCP Cloud Run), container instances are ephemeral. Local filesystem state is destroyed upon pod rescheduling or auto-scaling events.
3. **Relational Integrity & ACID Compliance**: Flat JSON lacks foreign key constraints, cascading deletes, index-accelerated querying, and transactional rollbacks.
4. **Pedagogical Governance & Dynamic Updates**: If cognitive parameters (BKT learning rates, slip/guess probabilities) or curriculum taxonomy (prerequisite DAG edges) are hardcoded into static JSON files, modifying them requires rebuilding and redeploying backend containers.

However, JSON *is* the recognized standard for two specific non-operational use cases:
- **Offline Evaluation Artifacts**: Benchmark runs and test reports (e.g. `backend/evals/benchmark_report.json`), analogous to `pytest-report.json` or `coverage.json`.
- **Database Seeding Fixtures**: Initial curriculum seed templates (e.g. `data/seed_problems.json`, `backend/bkt/parameters.json`) used exclusively during cold boots or zero-network CI test fixtures.

## Decision
We implemented a strict **3-Tier Storage Hierarchy** where **PostgreSQL (Supabase) is the sole authoritative operational database**:

```
┌─────────────────────────────────────────────────────────────┐
│ TIER 1: AUTHORITATIVE PERSISTENT STORE (PostgreSQL/Supabase)│
│  - Relational tables: students, sessions, skills, problems   │
│  - pgvector (768-dim) cosine index for semantic curriculum   │
│  - Row-Level Security (RLS) & ACID multi-table transactions  │
│  - Authoritative BKT cognitive hyperparameters & DAG edges  │
└──────────────────────────────┬──────────────────────────────┘
                               │ Writes / Rehydration
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ TIER 2: DISTRIBUTED HOT CACHE & RATE LIMITING (Redis)       │
│  - Sub-millisecond session state caching across all pods    │
│  - Distributed rate limiting & query vector deduplication   │
└──────────────────────────────┬──────────────────────────────┘
                               │ Network Failure / Cold Boot
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ TIER 3: ZERO-CREDIT MOCK / OFFLINE CI SEED FIXTURES         │
│  - parameters.json & seed_problems.json                     │
│  - Used SOLELY for database migrations & offline test runs │
│  - Zero operational dependency during production execution  │
└─────────────────────────────────────────────────────────────┘
```

### Key Technical Implementations:
1. **Database Schema Extension (`scripts/migration_day6_cognitive_dag_parameters.sql`)**:
   - The PostgreSQL `skills` table authoritatively stores all cognitive parameters:
     ```sql
     ALTER TABLE skills
       ADD COLUMN prior FLOAT DEFAULT 0.3,
       ADD COLUMN learn FLOAT DEFAULT 0.15,
       ADD COLUMN guess FLOAT DEFAULT 0.2,
       ADD COLUMN slip FLOAT DEFAULT 0.1,
       ADD COLUMN prerequisites TEXT[] DEFAULT '{}',
       ADD COLUMN retention_half_life_days FLOAT DEFAULT 21.0,
       ADD COLUMN decay_rate FLOAT DEFAULT 0.0385;
     ```
2. **Authoritative BKT Dynamic Synchronization (`backend/bkt/tracker.py`)**:
   - `sync_skills_from_db()` queries PostgreSQL `skills` table at runtime to hydrate cognitive hyperparameters and the Prerequisite DAG.
   - If educational researchers or teachers tune a skill's guess/slip parameters or add prerequisite edges in the database, the running application dynamically updates without service interruption or code deployment.
3. **Idempotent Unified Database Seeder (`scripts/seed_db.py`)**:
   - Seeds both curriculum problem vectors (`pgvector`) and Common Core skills with full cognitive parameters into PostgreSQL in a single automated step.
4. **Explicit Separation of Evaluation Artifacts**:
   - `backend/evals/benchmark_report.json` is formally designated as an immutable CI/CD evaluation artifact generated by the offline test harness, not an operational store.

## Consequences

### Positive
- **Enterprise-Grade Scalability**: The application runs completely stateless on the backend, permitting arbitrary horizontal scaling across multi-worker Uvicorn nodes and Kubernetes pods.
- **ACID Data Integrity**: All student mastery, sessions, and events use relational foreign keys with cascading constraints.
- **Zero-Downtime Curriculum Tuning**: Modifying skill prerequisite DAGs or Ebbinghaus decay parameters is executed via standard SQL migrations rather than code commits.
- **Offline CI/CD Independence**: Offline test harnesses and zero-credit unit tests continue to function flawlessly using fallback seed fixtures without requiring live cloud database connections.

### Negative / Trade-offs
- Requires maintaining SQL migration files (`scripts/migration_*.sql`) alongside schema definitions.
- Local developers must either supply Supabase database credentials or rely on the deterministic cold-boot fallback mode for isolated local unit tests.
